## Build a test blueprint that links chart types to visualization tasks <!-- role: advice -->

Create a test blueprint table that enumerates which visualization types are included and which reading/interpretation tasks each type will be assessed on.

## Why explicit coverage mapping prevents construct gaps <!-- role: reason -->

A blueprint forces you to state the intended content domain (chart types) and cognitive domain (tasks) before item writing, which reduces accidental omissions and overrepresentation. It also creates an auditable artifact for content validity review because experts can evaluate whether coverage matches the construct.

**Mechanism:** An explicit matrix of content × task supports systematic item generation and supports validity arguments by showing intended coverage.

**Evidence:** A visualization literacy test was developed using a blueprint that mapped 12 visualization types to eight visualization tasks, and the blueprint guided item generation and expert review for content validity [@leeVLATDevelopmentVisualization2017].

**Notes:** Empty blueprint cells should be interpreted as “not prioritized/suitable for this assessment,” not “impossible.”

## When you are designing an assessment or structured training coverage <!-- role: context -->

- **User Goal:** Ensure the assessment/training covers representative visualization types and task demands.
- **Task:** Plan item or exercise allocation across types and tasks.
- **Data:** Mixed dataset types (tables, hierarchical, geographic) that motivate different charts.
- **Chart Setting:** Standardized test, benchmark study, curriculum module.
- **Audience:** Non-expert users; mixed familiarity across chart types.
- **Success Criterion:** Clear, reviewable coverage with traceability from definition → blueprint → items.

## When not to rely on a blueprint alone <!-- role: exceptions -->

**Break it when:** The environment is highly interactive and the construct includes interaction discovery and use. **Why:** A static blueprint focused on read/interpret tasks will not represent interaction-dependent competencies.

## Tradeoffs of blueprinting <!-- role: costs -->

**Sacrifice:** Upfront planning time and the need to justify inclusion/exclusion decisions. **Risk:** Over-constraining the instrument to what is in the blueprint even when new needs emerge. **Mitigation:** Version the blueprint and document rationale for changes.

## Common blueprint failure modes <!-- role: mistakes -->

**Mistake:** Choosing tasks first and letting visualization types drift opportunistically. **Why it fails:** Coverage becomes unbalanced and content validity becomes harder to defend.

## Quick checks for blueprint quality <!-- role: check -->

**Failure Sign:** Many items target the same easy tasks (e.g., single-point lookup) while other intended tasks have no items. **Quick Check:** Count items per cell (type × task) and compare to intended coverage. **Stronger Test:** Ask independent experts to judge whether the blueprint matches the construct and target population.

## What to do if coverage is unbalanced or unclear <!-- role: fix -->

- Reduce the number of visualization types if you cannot cover their key tasks with enough items.
- Merge or redefine tasks so each task is observable and testable from the displayed encoding.
- Add dataset-type notes per visualization to ensure tasks are compatible with the underlying structure.
- Use the blueprint to drive item writing quotas per task and per visualization type.
