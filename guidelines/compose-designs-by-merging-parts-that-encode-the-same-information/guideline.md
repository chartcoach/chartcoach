## Merge shared encodings when composing multiple relations <!-- role: advice -->

Compose multi-relation graphics by merging axes or mark sets that encode the same domain information, rather than duplicating them in separate subcharts.

## Why merging shared encodings creates coherent presentations <!-- role: reason -->

A wide variety of designs can be generated by composing primitive graphical languages, and composition is most coherent when it merges identical encodings of the same information. This reduces redundancy and helps the combined graphic behave like a unified “sentence” rather than separate panels.

**Mechanism:** Merging shared axes or shared mark identity preserves semantic alignment across relations and avoids repeated scaffolding that fragments attention.

**Evidence:** A principle of composition is defined as composing designs by merging parts that encode the same information, implemented via operators that merge identical axes or compatible mark sets [@mackinlayAutomatingDesignGraphical1986b]. Examples include multiple scatter plots sharing both axes and aligned bar charts sharing a single axis domain [@mackinlayAutomatingDesignGraphical1986b].

**Notes:** Composition operators depend on expressiveness-compatible semantics (the merged parts must encode the same domain sets).

## When this applies <!-- role: context -->

- **User Goal:** Present multiple related relations in a single coherent graphic.
- **Task:** Compare relations that share domain sets or scales.
- **Data:** Relations with shared domain sets (same X, same Y, or same item identity).
- **Chart Setting:** Static 2D layouts where shared axes/marks can be merged.
- **Audience:** Readers benefiting from consistent frames of reference.
- **Success Criterion:** Reduced redundancy and improved integrative reading across relations.

## When not to follow it <!-- role: exceptions -->

**Break it when:** The components do not encode the same domain information (for example, different scales or different domain sets). **Why:** Merging would create false semantic equivalence and can break expressiveness [@mackinlayAutomatingDesignGraphical1986b].

## Tradeoffs <!-- role: costs -->

**Sacrifice:** Merged designs can become dense, requiring careful layout or legend support. **Risk:** Improper merging can force conflicting constraints (for example, incompatible mark positions) that prevent a valid composition. **Mitigation:** Fall back to less-integrated compositions (such as aligned views) when mark merging fails.

## Common mistakes <!-- role: mistakes -->

- **Mistake:** Combining charts side-by-side without aligning or merging their shared axes. **Why it fails:** It preserves redundancy and weakens cross-relation comparison because frames of reference differ [@mackinlayAutomatingDesignGraphical1986b].
- **Mistake:** Merging elements that look similar but do not encode the same domain set (for example, axes with different scales). **Why it fails:** It implies equivalences that are not true in the data [@mackinlayAutomatingDesignGraphical1986b].

## Quick tests <!-- role: check -->

**Failure Sign:** The composed graphic repeats the same axis or category list multiple times without need. **Quick Check:** Identify domain sets shared across relations and verify they appear once in the composed output. **Stronger Test:** For each merged element, state the exact domain set it encodes; if the statements differ, do not merge.

## What to do instead <!-- role: fix -->

- Use double-axes composition when both X and Y domain sets are identical across components.
- Use single-axis composition when only one axis domain set is shared and needs alignment.
- Use mark composition when marks represent the same domain values and constraints do not conflict.
- Keep components separate when no meaningful shared encoding exists, and ensure each remains expressive on its own.
