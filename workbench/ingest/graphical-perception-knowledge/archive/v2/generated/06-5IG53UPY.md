## Guidance

When visualizing a journey or process along a 2D path, encode the passage of time using discrete ticks (segment length) rather than a continuous color gradient or changing line thickness.

## Why

Experiments show that people are significantly more accurate at estimating time when it is represented by the spacing of ticks along a path. The discrete segments make it easier to perceive duration and to infer speed (from the segment length) compared to judging subtle changes in a continuous color ramp or stroke thickness. Using color to encode time is particularly ineffective and leads to large errors in judgment.

## When it applies

- When visualizing spatio-temporal data, such as a trip on a map, animal movement, or sports analytics.
- When the path is a 2D+time trajectory, meaning the X/Y position is already used for spatial or other data dimensions, leaving time to be encoded with other visual variables.
- When it is important for the audience to estimate a specific point in time (e.g., "Where was the object halfway through its journey?") or to understand the rate of travel.
- For both straight and smoothly curved trajectories.

## Exceptions

- If the path is extremely cluttered or is laid over a background with conflicting linear markings (e.g., a dense grid or contour lines), ticks may add to the confusion.
- On paths with many sharp corners or self-intersections, ticks can become distorted, overlap, or be visually ambiguous. In these cases, another encoding might be necessary, though likely less effective.
- If speed is the single most important variable to communicate, directly encoding it with color value may be more effective than having users infer it from segment length.

## Trade-offs

- **Clutter:** Adding ticks introduces more ink to the chart, which can increase visual complexity compared to a simple, clean line.
- **Speed Perception:** While speed can be inferred from segment length, this is an indirect perception. Directly encoding speed with color may be faster for tasks focused only on speed, though combining color-for-speed with ticks-for-time was found to be a very effective combination.

## Evaluate

- [ ] Is time encoded using a continuous color ramp (e.g., light blue to dark blue)?
- [ ] Is time encoded using the thickness (size) of the line?
- [ ] Is there no clear, discrete representation of time intervals along the path?

## Repair

1.  Replace the color or size encoding for time with discrete, regularly-spaced time ticks along the trajectory.
2.  If conveying speed is also a primary goal, add a color encoding for speed *on top of* the time ticks. This combination performs very well for both time and speed perception.
3.  If ticks are not feasible due to clutter, your next best (but significantly less accurate) option is to encode time with line thickness (size). Avoid using color for time.
